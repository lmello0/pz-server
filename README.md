# pz-server

Terraform configuration that deploys a [Project Zomboid](https://projectzomboid.com/) dedicated server on AWS, with a management script to start/stop it and keep costs down between sessions.

You bring an AWS account and a domain on Cloudflare (optional); this repo brings the networking, the EC2 instance, the game install, persistent save storage, automated backups, a spend alert, and DNS.

## What this actually builds

Everything lives in Terraform modules under `modules/`, wired together from the root `main.tf`. Each module owns one concern:

| Module | What it creates | Why it's separate |
|---|---|---|
| `network` | VPC, subnet, internet gateway, route table, security group | Nothing else can exist without a network to live in |
| `compute` | EC2 instance (t3.large, Ubuntu 22.04), SSH key, Elastic IP, generated passwords | The actual server |
| `storage` | A separate EBS volume for save data | Decoupled from the instance so it **survives instance rebuilds** |
| `backup` | AWS Data Lifecycle Manager policy + IAM role | Automated daily snapshots of the save volume |
| `budget` | AWS Budget with email alerts | A safety net for a learning account — it does not cap spending, only warns you |
| `dns` | A Cloudflare DNS record | Gives you `pz.yourdomain.com` instead of a raw IP that changes |

### The one thing worth understanding before anything else

**The save volume is separate from the instance on purpose.** The EC2 instance can be destroyed and rebuilt at any time — Terraform does this automatically whenever the boot script (`install.sh.tpl`) changes — and your world survives, because it lives on its own EBS volume that isn't touched by that process. The boot script checks whether the volume already has a filesystem on it; it only formats it once, the very first time. Everything after that is a mount, not a wipe.

This also means the volume has `prevent_destroy = true` set on it in Terraform. If you ever run `terraform destroy`, it will refuse to delete the save volume — on purpose. You'd have to remove that line deliberately first.

## How the server actually boots

There's no custom AMI here — a stock Ubuntu 22.04 image is provisioned at boot time via a `user_data` script (`modules/compute/install.sh.tpl`), which:

1. Installs SteamCMD via apt (enabling the `multiverse` repo and 32-bit support it needs), pre-accepting Steam's EULA so it doesn't hang waiting for input it'll never get.
2. Waits for the save-data EBS volume to attach, formats it **only if blank**, and mounts it at `/home/steam/Zomboid`.
3. Downloads Project Zomboid (Steam App ID `380870`) with a retry loop — SteamCMD's *first* invocation on a fresh machine reliably fails while it self-updates; the second succeeds. This was verified by hand across several rebuilds, not guessed.
4. Caps the JVM heap at 5GB (the shipped default asks for 16GB, which would OOM-crash on this instance's 8GB of RAM).
5. Writes `servertest.ini` — **only if one doesn't already exist on the save volume** — with a server password and whitelist mode (`Open=false`) enabled. Because it lives on the persistent volume, in-game config tweaks you make later aren't overwritten on a rebuild.
6. Sets up a systemd service (`zomboid.service`) that starts the server, restarts it on crash, and — critically — shuts it down **gracefully**: a small wrapper feeds the server from a named pipe, so `systemctl stop` can write `quit` into it and let Project Zomboid save the world before exiting, instead of being killed mid-flight.

Three passwords are generated by Terraform (`random_password`), never hand-typed: an admin/RCON password, a server join password, and a separate RCON console password.

## Prerequisites

- An AWS account, with the AWS CLI installed
- Terraform >= 1.7
- An SSH key pair (the setup script can generate one for you)
- Bash — Git Bash or WSL on Windows, native on macOS/Linux
- Optional: a domain managed on Cloudflare, if you want a hostname instead of a raw IP

### AWS IAM setup (one-time, manual)

Terraform needs an IAM user with programmatic access — not your root account credentials.

1. AWS Console → IAM → Users → Create user (e.g. `terraform-deploy`)
2. Attach `AmazonEC2FullAccess` to start. If you enable the backup or budget modules, you'll also need the extra permissions in `iam-policy-additions.json` (DLM, budgets, and a scoped `iam:PassRole` so Terraform can hand a role to DLM — and only to DLM)
3. Create an access key (choose "Command Line Interface" as the use case)
4. Configure a named CLI profile:
   ```
   aws configure --profile pz-server
   ```
5. Verify it: `aws sts get-caller-identity --profile pz-server`

## Setup

Clone the repo, then run the interactive setup script:

```bash
chmod +x pz.sh
./pz.sh setup
```

This walks you through everything and writes `terraform.tfvars` for you:

- **Your public IP**, auto-detected (forced to IPv4 — if you're on a dual-stack connection, `curl`-ing your IP by default can return IPv6, which won't work here since the security group is IPv4-only). This locks down SSH and RCON to just you.
- **An SSH key pair** — point it at an existing one, or let it generate `ed25519` keys for you.
- **Budget alert email** and monthly threshold.
- **Cloudflare** (optional) — your zone ID and an API token scoped to `Zone:DNS:Edit` on that one zone (use the "Edit zone DNS" template when creating the token; don't use the Global API Key).

If you'd rather do it by hand, copy `terraform.tfvars.example` to `terraform.tfvars` and fill in the same values.

**`terraform.tfvars` and `*.tfstate` are both gitignored, and for the same underlying reason: `terraform.tfstate` stores every generated password in plaintext.** Never commit either.

Then:

```bash
terraform init
./pz.sh start
```

First run takes roughly 10 minutes — most of it is Project Zomboid's ~5.3GB download happening inside the instance's boot script, after Terraform itself has already finished.

## Day-to-day use

```bash
./pz.sh status   # what's running, what's costing money
./pz.sh start    # bring the server up
./pz.sh stop     # save the world, shut down, ask about releasing the Elastic IP
./pz.sh ssh      # shell into the box
./pz.sh logs     # follow the game server's log live
```

`./pz.sh stop` is the important one to use rather than stopping the instance directly from the AWS console: it SSHes in first and asks systemd to stop the game service, which triggers the graceful-save wrapper described above. If it can't reach the server over SSH, it warns you and asks for confirmation before shutting down anyway, rather than silently losing whatever's happened since the last autosave (every 15 minutes by default).

## Cost model — why it's built this way

This is a **manual start/stop** setup, not an always-on server. That one decision has consequences threaded through the whole repo:

- **The Elastic IP is optional** (`use_elastic_ip` in `terraform.tfvars`). AWS bills for an Elastic IP whenever it isn't attached to a *running* instance — including while the instance is simply stopped. `./pz.sh stop` offers to release it; `./pz.sh start` re-allocates one and the Cloudflare DNS record updates automatically, since it's wired to read `module.compute.public_ip` rather than a hardcoded address.
- **Stopping the instance** (as opposed to destroying it) stops compute billing entirely. What's still running up a small charge: the two EBS volumes (root + save data) and daily snapshots — a few dollars a month at most.
- **The budget module is a smoke alarm, not a fire suppressant.** It emails you at 80% and 100% of actual spend, and separately when AWS *forecasts* you'll exceed the limit by month's end. It cannot stop anything from running.

## Retrieving secrets

Passwords are marked `sensitive` in Terraform outputs, so they don't get printed by default:

```bash
terraform output -raw server_password   # give this to friends
terraform output -raw admin_password    # in-game admin / RCON
terraform output -raw rcon_password     # RCON console — keep private
```

To let a friend actually join, you also need to whitelist their account once connected (this server runs `Open=false`):
```
/adduser <username> <password>
```
run as an admin, either in the in-game chat or over RCON.

## Repo layout

```
.
├── main.tf                      # wires all modules together
├── variables.tf                 # root-level inputs (your IP, email, Cloudflare creds, etc.)
├── outputs.tf                   # connection info + secrets, read via `terraform output`
├── providers.tf                 # aws, random, cloudflare provider requirements
├── pz.sh                        # setup / start / stop / status / ssh / logs
├── terraform.tfvars.example     # template — copy to terraform.tfvars and fill in
├── iam-policy-additions.json    # extra IAM permissions needed for backup + budget modules
└── modules/
    ├── network/                # VPC, subnet, IGW, routing, security group
    ├── compute/                 # EC2 instance, key pair, Elastic IP, boot script
    │   └── install.sh.tpl       # the actual server install/config/systemd logic
    ├── storage/                 # persistent EBS volume for saves
    ├── backup/                  # DLM snapshot policy + its IAM role
    ├── budget/                  # AWS Budget + email alerts
    └── dns/                     # Cloudflare A record
```

Every `.tf` file has its path as its first-line comment (e.g. `# pz-server/modules/network/main.tf`), so a snippet copied out of context still says where it belongs.

## Known limitations / things to know

- **Region is fixed to `sa-east-1`** (São Paulo) by default — change `aws_region` in `terraform.tfvars` if you're elsewhere; it isn't auto-detected.
- **PZ's whitelist (`Open=false`) is account-based, not Steam-ID-based** — players get a username/password via `/adduser`, not an automatic Steam ID check.
- **`servertest.ini` is only written once.** If you want to reset server settings, you currently have to edit or delete that file on the save volume by hand (over SSH) rather than through Terraform.
- **No mods support wired up yet** — the install script installs vanilla Project Zomboid. Adding Workshop mods means extending `install.sh.tpl`.
- Instance replacement (any change to `install.sh.tpl`) triggers a full ~5.3GB re-download every time, since there's no custom AMI baking the game in ahead of time.
